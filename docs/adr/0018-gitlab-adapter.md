# 0018. Thin hand-written HTTP client for the gitlab adapter

- Status: accepted
- Date: 2026-10-12
- Decided by: Opus (second opinion: none)

## Context

lazyforge needs a GitLab adapter (#137, #138) that serves gitlab.com and self-managed GitLab. GitLab addresses projects by numeric ID or by URL-encoded full path, puts subgroups in that path (`group/sub/repo`), reports CI as pipelines rather than per-commit checks, and fixes the merge method per project. gitlab.com allows 2,000 requests a minute per user today, and its Free tier drops to a 100-a-minute burst and 5,000 an hour from 2026-10-19. No gitlab.com token is wired up, so everything below comes from docs.gitlab.com (read 2026-10-12), not from a live server.

## Decision

- `internal/forge/gitlab` uses its own small `net/http` client, as the gitea and github adapters do (ADR 0005, ADR 0017), with no new module. It sends `PRIVATE-TOKEN: <token>`. The API root is `<web root>/api/v4`, and `Info().URL` stays the web root. `New` reads `GET /user`, `GET /personal_access_tokens/self` and `GET /metadata` (`/version` is deprecated), so a bad token fails at connect. A token whose `scopes` list is non-empty and has no `api` fails there too, with `ErrReadOnly`, and onboarding says so. Any error on the scopes read, and an empty `scopes` list (a granular token), lets the connection go on, so a token the check can't judge meets its limits on its first write. `Probe` reads `GET /metadata` without a token and takes a 401 `{"message":"401 Unauthorized"}`, or a 200 with a `version`, as GitLab.
- **Token on redirects:** Go forwards a custom header like `PRIVATE-TOKEN` to every redirect target, and strips `Authorization` only across domains. The adapter wraps the caller's `*http.Client` once, in `newForge`, with a `CheckRedirect` that deletes both headers on any hop off the web root's origin and stops after 10 redirects, so every call (API, `JobLog`, `OpenAsset`) keeps the token on the GitLab host.
- **Addressing:** every call names the project by its URL-encoded full path (`/projects/group%2Fsub%2Frepo`), built from `RepoRef`, so the adapter holds no path-to-ID state. `RepoRef.Owner` is everything before the last slash of `path_with_namespace`. Go keeps the encoding in `URL.RawPath` and sends it on the request line.
- **Pagination** sends `per_page=100` and follows `Link: rel="next"` until it is absent, never stopping on a short page. A next link off the API origin is an error, as in ADR 0017. It uses offset paging only, because keyset paging doesn't support the orderings the lists need.
- **No conditional-request cache.** GitLab doesn't document ETag or 304 on its REST API, and nothing says a 304 would cost no rate-limit budget. Instead, the adapter keeps the calls per refresh low (CI below).
- **Rate limits:** a 429 waits for `Retry-After` (seconds or an HTTP date, capped at 60 seconds, cancelled with the context) and retries once. A second 429 is `ErrRateLimited`, never `ErrUnauthorized`.
- **CI:** the MR list carries no `head_pipeline`, so `ListChangeRequests` reads one page of the project's newest 100 pipelines. Each MR gets the newest pipeline at its `sha` on its merge request ref (`refs/merge-requests/<iid>/head`), else the newest at its `sha` on its source branch, because GitLab lets the merge request pipeline decide whether an MR can merge. A pipeline on another ref, such as another MR's or a tag, never matches. An open MR with no match gets one `GET …/merge_requests/:iid` for its `head_pipeline`, which covers merged-results pipelines, whose SHA differs, and fork pipelines, which the target's list never shows; those GETs run four at a time. Merged and closed MRs skip that GET and get none, so paging old history stays cheap. A 403 or 404 on the pipelines listing, as on a project with CI/CD disabled, means no MR has CI and no per-MR GET is made; an empty listing still takes the per-MR GETs, for fork MRs. `GetChangeRequest` always uses `head_pipeline`. The fold is `failed` → fail; `canceled`, `canceling` → cancelled; `running` → running; `success` → pass; `skipped` → skipped; no pipeline → none; every other status, known or not, → pending, so it never reads as green. External commit statuses already land in a pipeline, so there is no separate status fold.
- **Merge:** GitLab has no per-call merge method, so the method is always the project's. `Merge` reads `GET /projects/:id` and sends `PUT …/merge` with the confirmed `sha`. It sends `squash` only when the project forces it: true for `always`, false for `never`. Under `default_on` and `default_off` it leaves `squash` out, so the MR's own squash choice stands. A non-empty `MergeOpts.Method` other than the project's is `ErrUnsupported`. `Repo.MergeStyle` uses the gitea strings the merge dialog already shows: `squash` when `squash_option` is `always` or `default_on`, else `merge`, `rebase-merge` (`rebase_merge`) or `fast-forward-only` (`ff`).
- **Access:** the higher of `permissions.project_access` and `group_access`: 40 and 50 → admin, 30 → write, lower → read; archived → read. When both are null, as they often are for inherited membership, one extra paged `GET /projects?membership=true&min_access_level=30&simple=true` marks those projects write.
- **Errors:** 401 → `ErrUnauthorized`, except on merge and approve, where GitLab uses it for "you may not" and it is `ErrRefused` with GitLab's message. A 403 on a read (`GET` or `HEAD`) → `ErrUnauthorized`, and a 403 on any write → `ErrRefused`, because there it means branch protection or a role too low for the action, not a bad token. 404 → `ErrNotFound`, merge 409 → `ErrHeadChanged`, and 405, 406, 422 and other 409s → `ErrRefused`. `message` is a string or a `{field: [errors]}` object, and both are read. GitLab's message is kept on every sentinel error.
- **Images** (#143): GitLab writes uploads as `/uploads/<secret>/<file>`, relative to the project, which core's repo-page resolution would lose to the host root. The adapter implements `forge.AssetResolver`, which core asks before its own resolution: it maps `/uploads/<secret>/<file>` under `<web>/<owner>/<name>/` and `/-/project/<id>/uploads/<secret>/<file>` under the web root, without I/O, and leaves every other link to core. Core still applies its credential, fragment and same-origin checks to the result. `OpenAsset` (ADR 0016) refuses a URL off the web root's origin with `ErrUnsupported`, rewrites an upload URL to `GET /api/v4/projects/<id or encoded full path>/uploads/<secret>/<file>` (GitLab 17.4 and later; the web route doesn't take a token) and fetches any other on-origin URL as is. An older server answers 404, which is `ErrNotFound`, so the image stays a link.
- **README:** `GetReadme` lists the tree with no `ref` and reads the file at `ref=HEAD`, so GitLab uses the default branch and no `GET /projects/:id` is spent to learn it. Core passes its cached default branch to `ListTree` and `ReadFile` when the caller's ref is empty, which spares those calls the same lookup.
- **Issues and comments** are user content (ADR 0006): issues are listed with `issue_type=issue`, so incidents, test cases and tasks never appear, and notes with `system: true` are dropped.
- **Runs, jobs, log, labels** (#139): `ListRuns` reads one page of `GET …/pipelines?order_by=id&sort=desc` (100, newest first, ADR 0017's runs exception) with `ref` and `sha` from the filter, and folds `status` with the CI fold above. `Duration` comes from `duration` when the list carries it (GitLab 19.4 and later) and is zero otherwise, with no per-pipeline GET. `ListJobs` pages `…/pipelines/:id/jobs`, which leaves out retried and trigger jobs, and fills `Job.Stage`. `JobLog` streams `…/jobs/:id/trace` untouched, ANSI and `section_start` markers included. `Labeler` reads `GET …/labels` (group labels included); `SetLabels` maps IDs to names through that list and fails on an unknown ID, because `PUT` with an unknown name would create a label. It lists labels once per call and reuses the list for the response; clearing lists them only if the response still carries labels. Hex colors lose their `#` as in the gitea adapter, and a CSS color name becomes "". `Rerunner` stays undefined (ADR 0006).

## Consequences

- No new modules, and the adapter shares its shape with gitea and github, so one review pattern covers all three.
- An open-MR refresh costs the MR list, one pipelines page, and one GET per MR whose head isn't in the newest 100 pipelines. A busy project with many stale MRs pays that N+1.
- Without a cache, an unchanged refresh costs the same as a changed one. On the 2026-10-19 Free-tier limits that bounds how often a large account can refresh.
- Every endpoint is unverified until it runs against gitlab.com, and the fixtures are synthesised from the docs.

## Alternatives

- `gitlab.com/gitlab-org/api/client-go`: rejected. It adds a module and a large type surface to convert from, as ADR 0017 found for `go-github`.
- Numeric project IDs with a path-to-ID map: rejected. It is state to keep in sync for no gain, since every endpoint takes the encoded path.
- A per-MR GET for `head_pipeline` on every list: rejected for the request count; the pipelines page answers most MRs in one call.
